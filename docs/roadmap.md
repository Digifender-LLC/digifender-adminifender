# Implementation roadmap

Tracks delivery of the [baseline phases](specifications/baseline.md#delivery-phases) in small reviewable slices. Status words follow [AGENTS.md](../AGENTS.md): **planned**, **implemented**, **locally verified**, **staging verified**, **production accepted**. Only the staging Worker is deployed, with synthetic data ([ops/staging.md](../ops/staging.md)); no slice is staging verified or production accepted.

| 14. Android app: Gradle toolchain, Room, sync, Compose screens | FR-002, FR-009, FR-010, FR-012, FR-019, FR-023, FR-025 to FR-029, FR-033, AT-04, AT-07, AT-08, AT-09, AT-10, AT-15 | Locally verified (JVM tests, Lint, release and staging builds); no emulator, device or live-service evidence | 14a: Gradle 9.8.0 wrapper with checksum, JDK 21, AGP 9.4.1, Kotlin 2.4.20, Compose BOM 2026.09.00, compile SDK 37, min SDK 31 (`android/gradle/libs.versions.toml`). `:core:model` JVM tests cover the concern controls (same table as the backend), optimistic edits that keep the server revision, outbox decisions (same idempotency key on resend, stale revision becomes a conflict, never an overwrite) and opaque push payload parsing. The app shell compiles, passes Lint with warnings as errors and builds an unsigned release. 14b: Room schema v1 (concerns, sources, pending mutations, sync state) and an OkHttp client with bounded responses. The sync engine sends queued edits first, in per-concern order with predicted revisions and a fixed idempotency key on every resend. It then pulls feed pages that commit together with their cursor; an expired cursor rebootstraps and keeps queued edits. Stale edits become conflicts that block later edits until the owner reapplies or discards them, and an expired session holds the queue. JVM tests use fakes, MockWebServer and the shared `sync-changes` contract fixture. Room store tests are compiled but need an emulator. 14c: a session layer for passkey sign-in (Credential Manager 1.6.0, no allowCredentials) and recent-auth confirmation. Tokens are sealed with a non-exportable Android Keystore AES-GCM key in no-backup storage. Access tokens are refreshed one at a time, and a refresh that has started is never cancelled, so a rotated refresh token is never replayed. A refused refresh requires sign-in again; an unanswered one keeps the token for later. A 401 marks only the refused token stale, and sign-out forgets tokens before revoking the family on the server. JVM tests cover the session rules and the `/auth` wire format; the Keystore vault test is compiled but needs an emulator. 14d: Compose sign-in, inbox, concern detail and settings screens backed by Room through `ConcernRepository` and view models. Queued edits show on top of the server copy and are marked unsent; conflicts and refused edits are listed first and only the owner reapplies or drops them. Controls are checked against what the owner sees. Freshness never claims a sync that did not happen, and cached items stay readable when the session needs a new sign-in. WorkManager runs periodic and on-demand sync under unique names. Sign-out names unsent edits, cancels sync and clears the cache. JVM tests cover the overlay, ordering, repository and a view model. 14e: FCM receiver and three notification channels (critical, review reminders, processing). A push is validated with the shared parser, shown with generic text, opens only a checked concern ID or the briefing, and triggers a sync; it never changes local state. A signed-out phone shows nothing. The Worker now sends data-only FCM messages, so the app draws the notification on the right channel, and it skips devices with no live session. Token and permission registration runs in WorkManager with a fixed idempotency key per attempt and a digest to skip repeats; Settings shows and requests the notification permission. Firebase config (`app/google-services.json`) is not committed. Without it, the build reports push as not set up. 14f: an Archive tab with archive and quarantine views listed from the synced Room cache, exact search over `GET /search` (sender and received-date filters, further pages through the cursor) and source detail over `GET /sources/{id}` and `/sources/{id}/chunks` with body text, attachment inventory and linked items. The concern screen lists its source emails. Search results always state their coverage: complete, partial while more archive partitions remain (order not final), or cached-only when offline, signed out or the server fails; cached-only search matches subjects, senders and the text of opened sources with literal, bound LIKE terms. Opened text is kept in a new Room table (schema v2, auto-migration from v1) only while the synced source has the same revision; sync prunes it in the same transaction as a deletion or change, a late response cannot bring deleted text back, and a deleted source disappears from an open screen. Bodies over 1,000,000 characters are kept in part and marked. JVM tests cover the repository, wire format and view models; the Room cache and migration tests are compiled but need an emulator. 14g: waiting form (follow-up at 09:00 local) and due-date picker recorded with its zone (DST test), plus a briefing screen. Mark reviewed uses one key per shown snapshot and acknowledges nothing, and a briefing notification opens it. 14h: grounded chat for all mail, one item or one email (Room schema v3, auto-migration from v2). The turn ID is the request identity, answers are polled with 1, 2, 5 and 10 s backoff, and an unconfirmed question is resent only by the owner, with the same ID. Claims show their basis and citations, and citations open the source. Deletion tombstones withdraw cached answers and quarantine withholds them. Route decoding accepts only known kinds with well-formed IDs. 14i: reviewed `archive.delete` from source detail and `device.revoke` from Settings. The server's preview is shown in typed form (an unreadable one cannot be confirmed) and confirmed with its digest under one key; a recent passkey is requested once when needed. No answer is reported as unknown, and a stale review must be reviewed again. Attachments and exports are saved only to an owner-chosen document, after a size and SHA-256 check for attachments; failed saves delete the partial file. Exports are created, polled and saved. 14j: the phone worker shares the server's readiness gate. It claims with the exact cloud prompt, heartbeats while generating, stops on severe heat, low battery or a lost lease, and declines input over 1,536 tokens through a new decline endpoint. LiteRT-LM 0.17.1 runs on the CPU. The model is an owner-chosen file, activated only when size and SHA-256 match a pinned manifest; none is pinned yet ([models/](../models/README.md)), and with no public tokenizer the input bound is UTF-8 bytes. Device PDF and OCR extraction adds a server protocol (migration 0011, Workers-runtime tests): meaningful embedded PDF text on API 35+, otherwise bundled ML Kit Latin OCR when policy allows. It works one page at a time (4 MP render, 16 MP image cap) in batches of 10 pages or 128 KiB, with checkpoints, a manifest-hash publish and a 100-page pause with Resume. Not covered: instrumentation runs (Room v2/v3 and Keystore tests are compiled only), screenshots and TalkBack, live passkeys and FCM, model latency, memory and quality, OCR accuracy on the 30-document corpus, and S24+ acceptance. |

## Next steps

All P1 slices have their code. What remains is evidence and owner setup ([ops/release.md](../ops/release.md), [ops/staging.md](../ops/staging.md)):

1. Emulator instrumentation runs (Room v2/v3 migrations, Keystore vault, chat invalidation), screenshots and TalkBack checks.
2. Owner accounts: set up Play App Signing and the internal track, create the Firebase apps (`google-services.json` per environment, never committed) and a staging email address, and enroll the owner on staging.
3. The local model, **deferred by the owner (2026-10-04)**: the device runner ships with no pinned manifest, so phone-routed work stays visibly queued and the server falls back to cloud or waits as routed. To resume, download `gemma3-1b-it-int4.litertlm` through its license page, record its SHA-256 and size in `models/`, and evaluate it on the S24+.
4. Physical S24+ acceptance: passkey sign-in, live FCM, OCR accuracy, memory and thermal behavior, and the Play-installed build (local inference latency once the model is resumed).
5. The recovery drill ([ops/recovery-drill.md](../ops/recovery-drill.md)) on staging, then production.
