## Review round 2: recurring export reconciliation (2026-10-09)

**Hole.** Round 1 stopped sweeping an export 30 minutes after it settled. The 15-minute Queue consumer bound does not bound an R2 request the runtime had already sent when the invocation ended, so a ZIP could land after the final sweep and stay indefinitely, and the planned (unconfigured) lifecycle rule does not change what the local implementation does.

**Change.** `expireExports` no longer has an end state. Every visit sets `cleanup_next_at` to `now + EXPORT_RECONCILE_MS` (6 hours), for invalidated, failed, expired, unscoped, abandoned and ready exports alike; a ready export keeps only its published pair and its next visit is `min(now + 6 h, expires_at)` so expiry is not delayed; an export that closed early still gets its second sweep when the 30-minute grace has passed. The pass takes the 50 exports that have been due longest (`COALESCE(cleanup_next_at, settled_at, created_at)`), one pass per minute, and lists only `exports/{id}/`. A failed list, delete or D1 update keeps the previous state (a failed expiry stays `ready` on record, and the download is refused as expired) and is retried 15 minutes later. A deletion that invalidates a ready export now clears `cleanup_next_at` so the published pair goes at the next pass, not at a reconciliation due hours later. Attempt-unique keys, the lease and membership guards and the admission symmetry are unchanged. No migration change (the existing `cleanup_next_at` column and `exports_cleanup` index carry the schedule); `swept_at` and `swept_full` are now bookkeeping only. `guardParams` lost a stray formatting slip in `runner.ts`.

**Capacity assumptions (design, not measured).** 50 visits per pass x 360 passes per interval = 18,000 exports per interval; each visit is one prefix listing (one page unless the prefix holds more than 1,000 objects), a delete only when something is found, and one D1 update. The rows are never pruned, so reconciliation work grows with the number of exports ever created. At a single owner's rate that is small, but it is unbounded in principle; pruning needs its own retention decision. The Workers per-invocation subrequest limit of the deployed plan was not checked against a full pass of 50 and must be before staging. A prefix with more objects than one invocation can list and delete is not handled beyond the existing chunking.

**Tests** (`export-cleanup.test.ts`, run with the clock moved forward; mutations listed below):
- An invalidated export (deleted while building, own cleanup failing): an object arriving after the grace sweep is not removed before the next reconciliation (checked one millisecond early), is removed at it, and a second object days later is removed again.
- A ready export whose superseded attempt lost its lease: an object landing after the last grace sweep is removed at the next reconciliation, the winning ZIP, manifest, attempt and membership are untouched and the download keeps serving the same bytes; a failed reconciliation is retried 15 minutes later with the export downloadable throughout.
- Expiry: a ready export reconciled an hour before expiry is due at expiry; a failing expiry leaves it `ready` on record with the objects present and a 410 download, the retry expires it, and an expired export is still reconciled.
- A deletion that invalidates a ready export waiting for its reconciliation clears the schedule and the next pass removes the published pair.
- Fairness and no rescan: 60 overdue exports created in the opposite order to being due, one never-visited newcomer and one not yet due: the first pass handles exactly the 50 oldest-due, listing exactly their own prefixes (a count of the `list` calls, none for the whole bucket), the second pass the other 10 and the newcomer, the not-yet-due export is never listed, and a third pass lists nothing.
- Failures and delays: one export whose listing fails, one whose delete is slow and then fails, one healthy: only the healthy one is removed, both failures move to `now + 15 min`, are not retried before that, and are removed (and rescheduled 6 hours ahead) when the failure clears.

**Mutations** (each run alone on `export-cleanup.test.ts`, results read from each run's own output; only the last run's log file survived, because the next run overwrote it; every mutated file was restored and compared with a backup copy): invalidated-style export unscheduled after the grace (4 tests failed); ready sweep unscheduled (3 failed); never-visited rows ordered first (1 failed); deletion not clearing the schedule (1 failed); ready reconciliation not capped at expiry (1 failed).

## Behavior changes to know about

- `GET /exports/{id}` answers `500 export_manifest_unavailable` / `export_manifest_invalid` for a ready export whose manifest is missing or malformed, and a failing scheduled step now fails the cron invocation (after the other steps ran) instead of stopping them.
- The export manifest is `schemaVersion` 2 (adds `scope`, `sections`, omission reasons; rules and services are empty for a subset). `POST /exports` and `GET /exports/{id}` return `scope`, `createdAt`, `invalidatedReason` and `failureCode`. A job that ended in failure now shows as `failed` instead of staying `running`.
- A request that older code stored under a key (hash of `{}`) now conflicts instead of replaying; an export row without a scope is never built or downloaded and its objects are removed by the scheduled cleanup.
- Deleting a source no longer invalidates every ready export, only those whose published attempt contains it (exports still being built are invalidated as before).
- Migration `0011` (still uncommitted, so edited in place) adds `exports.attempt`, `settled_at`, `cleanup_next_at`, the `attempt` column of `export_sources` and the `export_uploads` table (round 3 removed `swept_at` and `swept_full`, which nothing read). Export objects now live under `exports/{id}/{attempt}/`.
- A `leased`/`running` job whose lease expired with 5 attempts spent is now ended as `dead` (`error_code:"lease_expired"`) instead of being claimed a sixth time and onward; every job kind is covered, and an export whose job ended this way reads `failed`.
- Partial concern lines have `null` for the withheld fields, and `export-status.invalidatedReason` has a new value, `admission_changed`.

## Not covered

No Android code, DTOs or screens; no WorkManager download, Keystore encryption or SAF export; no staging, live R2/D1 or restore behavior; large-archive exports remain one job without ZIP64 or resumption; text-query and label selection are client-side (complete search paging, then `sourceIds`); cleanup status says nothing about backups; `POST /operations/{id}/reconcile` and generic or external P3 reviews are not implemented.
