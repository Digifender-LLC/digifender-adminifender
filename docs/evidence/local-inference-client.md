# Local inference client (phone side): local verification evidence

Date: 2026-10-09. Scope: the phone's side of the Worker's existing `/device-work` inference API: readiness, claim, heartbeat, run, submit and decline, the model manifest and its verification, the LiteRT-LM adapter, Settings controls and the schedule. The Worker side was already in the repository (slice 11 and 12) and is unchanged. Status: **implemented and locally verified within the scope below**; **no model was installed or run**, and nothing ran on a phone.

## Result

Pinned toolchain, one session: `./gradlew :core:model:test :core:data:testDebugUnitTest :app:testDebugUnitTest :core:data:lintDebug :app:lintDebug :app:assembleStaging` exit 0, `BUILD SUCCESSFUL in 23m 48s`; **468 JVM tests** (`:core:model` 29, `:core:data` 372, `:app` 67), none failing; both Lint tasks passed; the staging APK built (97.6 MB). Worker, on Node 22.22.0: the inference, chat, contract and live-contract tests (565 and 37) passed with the new schemas checked against every live answer; the whole Worker suite was not re-run for this change because no Worker source changed.

## What was added

- **Shared contracts** `device-work-readiness`, `device-work-claim`, `device-work-result`, `device-work-result-answer` and `device-work-decline` (30 fixtures). The Worker's inference and chat tests now validate every claim, result and decline it accepts or answers against them, including a chat task, so a change on either side fails a test.
- **Phone wire layer**: strict parsers and an HTTP client (`HttpDeviceWorkApi`) for those five shapes. A triage task must name its email and revision and no turn, a chat task its turn and no email; an answer about another task, or one that is not the contract's shape, is "no answer" (the result is then resent under the same key), never a half-read task. Every shared fixture is accounted for (`DeviceWorkWireFixturesTest`), builders round-trip, and the client is tested against MockWebServer (`HttpDeviceWorkApiTest`).
- **Runner** (`DeviceWorkRunner`, ported with its tests from the 2026-10-04 staging branch): claims only when the OS-reported state admits the work (a loaded model, battery at least 30 %, thermal below severe, charging for background work or a foreground session for chat), declines input that might exceed 1,536 tokens, renews the lease while generating, stops on heat or low battery without submitting, and resends an unanswered result with the same key. Mutation checks, reverted afterwards: never declining oversized input (1 of 8 runner tests failed), skipping the readiness gate (1 failed). A first attempt ran the wrong test class and passed both mutants; the numbers above are from the corrected runs.
- **Model**: `ModelManifest` (pinned size, SHA-256 and limits; unknown fields refused), `ModelStore` (the owner chooses the downloaded file; it is copied into no-backup storage while being hashed and activated only on an exact match; nothing is bundled and no token is on the phone) and `LiteRtLmModel` on the CPU backend. LiteRT-LM is **0.18.0**, the latest release on Google Maven on 2026-10-09 (the earlier branch used 0.17.1); the adapter compiled unchanged. The token count is an upper bound (UTF-8 bytes plus framing) because the runtime exposes no tokenizer, so an input that might not fit is declined, never cut.
- **App**: Settings gets an "On-device model" section (not configured, not installed, installing, installed, wrong size or hash); a charging background run every 15 minutes when a model is installed; chat tasks are offered while a chat screen is showing, every 15 seconds; sign-out cancels the schedule; the chat wait text no longer says the phone cannot run a model.
- **Checks on the dependency** (built staging APK, not a device): `liblitertlm_jni.so` for `arm64-v8a` has 16 KB ELF alignment (`0x4000`); no permission was added.

## Not covered, and not claimed

- **No model is pinned or installed.** The build has no manifest (`-Padminifender.modelManifest` was not given), so the phone reports "no pinned local model" and claims nothing. The SHA-256 of the Gemma files is hidden behind the model card's license gate, and the TDD's profile (2,048-token int4 `.litertlm`) matches no single file there; the candidates and the decision are recorded in [models/README.md](../../models/README.md).
- Model load time, latency, memory, thermal and cancellation behaviour, and the 50 fixed triage and chat cases (the TDD's model gate) were not measured: that needs the model and the S24+.
- The 200-message AT-05 corpus and recall gates, and the model-quality parts of FR-023 acceptance, stay open for the same reason.
- Nothing was exercised against the staging Worker with a signed-in session, and staging does not run this change (it is phone code).
