## What is implemented

**Attachments.** `AttachmentInfo` and the Room-stored inventory now keep the `sha256` and `disposition` the Worker already sent (rows cached before schema v5 have no checksum and are refused for download until the email is opened again, which refreshes them). The owner asks for a file per attachment; the request is a Room row (`local_files`) written before the work is queued, with a fresh generation each time it is created or restarted. One WorkManager job per attachment (`attachment-<id>`) streams `GET /attachments/{id}/content` with no timeout on the call (per-read timeout instead), counts bytes against the inventory's size, hashes while writing, compares the `x-attachment-sha256` header and the final SHA-256 with the inventory, and only then makes the file available. The bound is the inventory size, at most 25 MiB, which is the Worker's raw admission ceiling (`MAX_RAW_BYTES`); the 20 MiB extraction limit is not the download limit. Bytes are sealed with standard AES-256-GCM, one message per file (`"ADMF"`, version, 12-byte nonce, ciphertext, tag), with the attachment ID and SHA-256 as associated data, under a separate non-exportable Android Keystore key (`adminifender.files.v1`), in `noBackupFilesDir/attachments` under opaque names. Files are opened whole and authenticated (at most 25 MiB in memory); there is no segmented or home-made scheme. A 500 MiB least-recently-opened cache is enforced in the transaction that commits a download. Commit is fenced by generation, by state, and by a re-read of the source row (deleted, quarantined or stricter than at request time refuses and removes the row). A late worker, a late response and a restarted request cannot make a purged file ready. A failed, cancelled or superseded run removes its partial and finished blobs immediately; start-up requeues interrupted rows and sweeps files no row names. Failure counts (including a connection lost part-way through a body) are capped at five attempts; the rows show their fixed error codes.

Files are removed on explicit sign-out and when the session is gone (`SignedOut` or `SignInRequired`); running downloads are aborted (their connections closed) and WorkManager work is cancelled. Cached text, queued edits, chat, deletion reviews and export intents are kept for an expired session. When sync removes a source, quarantines it or makes it stricter, its file rows go in the same transaction, and the app is told afterwards to stop their work and close their connections. There is no in-app viewer for anything but bounded plain text (txt, csv, md, json, log up to 256 KiB, strict UTF-8, no NUL); HTML, SVG, XML, PDF and images are never rendered, and nothing is opened by another app. "Save a copy…" writes the verified bytes to a document the owner creates through the Storage Access Framework and says that copy is outside the app and cannot be recalled.

**Deletion review.** Entry points are the email screen and a selection mode in the Archive tab (explicit limit of 50, refused out loud, never cut to a first page). The selection, the `POST /reviews` Idempotency-Key and the phase are stored before the request (`deletion_reviews`). The Worker's review is checked against the selection (same IDs, expected count, preview sources, source revisions) before it is offered; the screen shows the server's subjects (never stored), file count, concerns erased or detached, derived data, a fingerprint of the digest, and the expiry. Confirmation asks for a recent passkey (`SessionManager.confirmRecent`); the confirmation key is stored before the prompt, and after the prompt the row is re-read and re-validated (still the same review, unexpired, the emails unchanged on the phone) before it is marked `SENDING`, which is the commit point; a dropped, replaced, expired or changed review sends nothing. An answer is applied only to the row as it is now, only forward in phase, and only in the sign-in epoch it started in, so late responses cannot resurrect a dropped review or overwrite a settled receipt. A confirmation with no recorded answer stays **unknown**: it is read back (`GET /reviews/{id}`, then `GET /operations/{id}`), never re-dispatched, and a 404 or 410 is shown as "not known", not as "nothing happened". An `open` read-back is only a point in time; the owner may explicitly confirm again with the same key; an `expired` one settles as unused only a minute past the expiry. A successful receipt is stored first, then the phone removes the deleted emails' rows (with a tombstone guard so a stale sync page cannot bring them back), cached text, files and chat answers that rest on them. The screen shows the receipt as "hidden, tombstoned and recorded in the independent ledger", and cleanup (`pending`, `partial`, `complete`, `failed`, `unknown`) with the scope "live archive only; backups and export files are not covered" every time. It never says every byte is erased.

**Exports.** An export form offers everything, a date and address filter (from inclusive, before exclusive, exact lower-case sender and recipient) or the emails selected in the Archive (at most 1,000, otherwise the form says why it cannot be sent), with the admission (ordinary archive, quarantine only, or both) always chosen and always spelled out. The normalized scope and the key are stored before `POST /exports`; an unanswered request is only ever repeated as the same request, by the owner. A scope that comes back different from the one asked for is refused. States (`pending`, `running`, `ready`, `failed`, `expired`, `invalidated`) are read into Room before the screen shows them, in the foreground on a bounded schedule and in WorkManager; an older answer never takes back a settled state. The ZIP is streamed from the authenticated endpoint straight to the document the owner picked, and verified as it arrives without extracting anything: only stored entries without ZIP64, encryption or data descriptors; local headers, central directory and end record must agree; names must be plain relative paths; each entry's CRC and SHA-256 are computed on the fly; the manifest (schema version 2) must agree with the status the owner was shown (export ID, snapshot, creation time, scope, counts, omissions, sections) and list every other entry with the same size and SHA-256; the whole-ZIP SHA-256 is computed separately and labelled as such. The ceiling is the Worker's `0xffff_fffe` bytes and 65,535 entries; the manifest is bounded at 16 MiB. Only after all of that is the file called verified. A dropped connection, a failed check, a destination that cannot be written, a stopped download and a process that ended are different recorded states; the partial file is discarded when the destination allows it and the screen says whether that worked. Retrying is a download into a new destination, not a new export request. Omissions, partial concerns and omitted owner rules are shown. An export that is invalidated while its download finishes is read once more and shown as such next to the verified file.

**Room v5.** Additive auto-migration 4 to 5: `local_files`, `source_tombstones`, `deletion_reviews`, `export_intents`. Nothing existing changes. `5.json` is committed.

**Not implemented here, and not claimed.** The 90-day text window and pinned items: the existing code keeps opened source text until the source changes or is deleted and has no age-based expiry or pin, so 14i did not add or claim either. The attachment cache is the only retention rule added. Foreground-service downloads of very large exports: an export download runs in the app's process scope and is reported interrupted if the process ends. Image or document preview. Range or resumable downloads (the Worker offers none). Per-file deletion (the Worker deletes whole emails). Listing services (the Worker has no such call). Any change to the Worker.

## Existing defect found and fixed on the way

`HttpApi` read response bodies after returning from its IO dispatcher block, so every older read (`source`, `chunks`, `search`, sync, briefing, chat) consumed its body on the caller's dispatcher, which is the main thread for view-model calls. That would throw `NetworkOnMainThreadException` on a device for any body not already buffered. `execute` now waits for headers without blocking a thread, cancels the call when the caller is cancelled, and reads the bounded body on IO before returning. The new clients read bodies on IO as well. This was found by reading, not by a device run; nothing here proves it behaved either way on a device.

## Contract gaps for the Worker

1. `safeName` in `backend/src/exports/job.ts` keeps `.` and `..` as file names, so an attachment named `..` yields the entry `files/<source>/<attachment>/..`. The phone refuses to vouch for such a name (`verification_unsafe_name`), so one such attachment makes the whole export unverifiable. The Worker should map those names.
2. Neither `/exports/{id}/content` nor `/attachments/{id}/content` supports ranges, so an interrupted multi-hundred-megabyte export restarts from zero.
3. The raw attachment ceiling (25 MiB) is a constant in both code bases; the Worker does not publish it.
4. There is no call that lists exports, so an export made on another device or before sign-out cannot be rediscovered.
5. `archive.delete` takes whole emails; there is no review for removing one attachment.
6. The manifest does not say how many original `.eml` files were expired, only `sources.jsonl` lines do, which the phone does not parse (they hold full text); the screen states the rule in words instead.
7. The Worker still has no service-list call (unchanged from 14h).
